Command: cd build/stress; /eda/xilinx/2026.1/Vivado/bin/xsim stress -tclbatch ../../scripts/reproduce_run1.tcl. The supplied Tcl adds only waveform probes, no design/stimulus changes. Raw log: reproduction.log; raw trace: run1-reproduction.vcd; pre-edge samples: run1-cycles.csv.

The PROCESS response header transfers at 1420 ns. READY is withdrawn at 1424 ns, before any result is available. At 1516 ns the compute pipeline's ap_enable_reg_pp0_iter10 becomes 1, indicating the result is pending at its output stage. The first subsequent sampled rising edge is 1524 ns (cycle 191, numbering the first edge at 4 ns as cycle 1). It observes iter10=1, READY=0, block=1, VALID=0. The result remains pending until the test aborts at 1744 ns; this is a genuine dependency, not a false assertion during computation.

The retained generated compute RTL defines block = !READY && iter10 and VALID = !block && iter10, algebraically VALID = READY && iter10. Thus dropping READY after VALID is asserted can also drop VALID with a pending beat. The Run 1 test did not actually cover this second situation: it withdrew READY before the first result's VALID, and after accepting the two response headers. It also did not hold READY low before the first CONFIG response. Its stability assertion hardcoded TLAST=1 and therefore was insufficient for multi-vector payloads. Run 2 corrects these coverage gaps rather than treating old PASS checks as proof.

The unchanged Run 1 kernel was also re-synthesized in isolated build_repro_run1 (original-synthesis.log) and tested with the strengthened external-pin rtl_suite. The exact commands are scripts/reproduce_run1_synth.tcl and scripts/reproduce_run1_suite.sh. No current Run 2 source was changed for this reproduction.

Mode 0 (READY low before the first response) fails VALID_WAIT at cycle 290 / 2316 ns after the complete CONFIG payload. Mode 1 proves the stronger, availability-independent failure: VALID first rises at 276 ns with response ID zero and all legal sidebands; the sink lowers READY at 280 ns, and VALID immediately falls at 280 ns. The remembered pre-withdrawal beat is checked at the next rising edge, cycle 36 / 284 ns, producing STABILITY_WITHDRAW with VALID=0 and output fields unknown. This cannot be a testbench false positive caused by a word not yet being available: VALID itself advertised the word before READY changed.
